# ⚡ Практикум по нагрузочному тестированию (Performance Testing с k6)

> Нагрузочное тестирование проверяет, как ведет себя сервер под реальным потоком пользователей: удерживает ли он стабильное время отклика (Latency), не зависает ли база данных и при каком числе запросов в секунду (RPS) начинаются сбои.

---

## 🎯 Виды нагрузочного тестирования

1. **Smoke Test (Дымовой):** Минимальная нагрузка (1-2 виртуальных пользователя, 1 минута), чтобы проверить, что тестовый скрипт вообще работает и не выдает синтаксических ошибок.
2. **Load Test (Нагрузочный):** Проверка работы системы под ожидаемой стандартной пиковой нагрузкой (например, 20-50 одновременных пользователей в течение 10-30 минут).
3. **Stress Test (Стресс-тест):** Постепенное увеличение нагрузки выше предельно допустимой, чтобы найти **точку отказа (Breaking Point)** и посмотреть, как система восстанавливается после спада нагрузки.
4. **Spike Test (Всплеск):** Резкий моментальный скачок нагрузки (с 0 до 500 пользователей за 5 секунд), имитирующий маркетинговую рассылку или старт распродажи.
5. **Soak / Endurance Test (Тест на выносливость):** Средняя нагрузка в течение многих часов (12-48 часов) для поиска утечек памяти (Memory Leaks) и переполнения дискового пространства логами.

---

## 🚀 Как запустить нагрузочный тест

Скрипт написан на современном инструменте **k6** (от Grafana).

### Вариант 1: Через Docker (не требует установки k6 на ПК)
```bash
# Из папки automation-tests:
docker run --rm -i --network=host grafana/k6 run - < load/load-test.js
```

### Вариант 2: Если установлен локальный k6
```bash
# Установка на Windows через winget или choco:
# winget install k6 --source winget
# brew install k6 (macOS)

k6 run load/load-test.js
```

## 📊 Как читать и анализировать отчет k6

Пример вывода консоли после выполнения теста:

```text
     ✓ Каталог: статус 200
     ✓ Каталог: вернулся список товаров
     ✓ Фильтр: статус 200
     ✓ Фильтр: отклик быстрее 300мс
     ✓ Корзина: статус 200
     ✓ Заказ: статус 201

     checks.........................: 100.00% ✓ 1440      ✗ 0   
     data_received..................: 3.2 MB  64 kB/s
     data_sent......................: 420 kB  8.4 kB/s
     http_req_duration..............: avg=64.12ms min=12.1ms med=48.2ms max=412.8ms p(95)=180.4ms p(99)=310.2ms
     http_req_failed................: 0.00%   ✓ 0         ✗ 1200
     http_reqs......................: 1200    24.0/s (RPS)
     vus............................: 20      min=1       max=20
```

### Ключевые метрики для QA:
* **`http_reqs (RPS)`**: Количество выполненных запросов в секунду (в примере: 24 запроса/сек).
* **`http_req_failed`**: Процент упавших запросов (должен стремиться к 0.00%).
* **`http_req_duration`**:
  * **`avg` (среднее):** 64 мс.
  * **`p(95)` (95-й перцентиль):** 180 мс — значит, 95% пользователей получили ответ быстрее, чем за 180 мс. *В тестировании смотрят именно на перцентили p95 и p99, а не на среднее значение, потому что редкие сильные зависания смазываются в среднем!*
  * **`max`:** самый долгий запрос (412 мс).
* **`checks`**: 100% — все наши функциональные проверки бизнес-логики подтвердились.
