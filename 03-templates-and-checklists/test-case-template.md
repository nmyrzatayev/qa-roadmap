# Шаблоны тест-кейса и чек-листа

> Тестовая документация должна быть лаконичной, не требовать часов на поддержку и быть понятной любому члену команды.

---

## 1. Шаблон классического Тест-кейса (Test Case)

Используется для критического функционала (оплата, регистрация, ядро бизнес-логики) или при передаче тестирования внешним подрядчикам.

```markdown
### [TC-AUTH-001] Успешная авторизация пользователя по валидному Email и Паролю

- **Модуль**: Авторизация / Аутентификация
- **Приоритет**: High (Smoke)
- **Тип**: Функциональное / Позитивное
- **Автор**: QA Engineer

#### Предусловия (Preconditions):
1. В базе данных существует активный пользователь с email: `valid_user@test.com` и паролем: `SecurePass123!`.
2. Пользователь находится на странице `/login`.

#### Шаги выполнения (Steps):
| № | Действие (Action) | Ожидаемый результат (Expected Result) |
| :-: | :--- | :--- |
| 1 | Ввести `valid_user@test.com` в поле "Email" | Текст отображается в поле без ошибок подсветки |
| 2 | Ввести `SecurePass123!` в поле "Пароль" | Символы маскируются точками (`••••••••`), доступна иконка "Показать пароль" |
| 3 | Нажать кнопку "Войти" | 1. Кнопка переходит в состояние загрузки (спиннер).<br>2. Запрос `POST /api/v1/auth/login` завершается с кодом `200 OK`.<br>3. В cookie записывается JWT токен (`HttpOnly`). |
| 4 | Дождаться завершения перехода | Происходит редирект на URL `/dashboard`. В правом верхнем углу отображается имя пользователя `Valid User`. |

#### Постусловия (Postconditions):
- Нажать "Выйти из системы" для очистки активной сессии.
```

## 2. Шаблон гибкого Чек-листа (Agile Checklist)

В современных продуктовых командах чек-листы используются чаще тест-кейсов: они пишутся за 5–10 минут и легко поддерживаются.

### Формат: [Компонент / Сценарий] — [Проверка]

```markdown
### Чек-лист: Форма смены пароля в профиле

#### Позитивные проверки:
- [ ] Успешная смена пароля при вводе валидного текущего и нового пароля (8+ символов, спецсимвол, цифра)
- [ ] Завершение всех остальных активных сессий на других устройствах после смены пароля
- [ ] Отправка уведомления на email о факте изменения пароля

#### Валидация полей (Граничные значения & Негатив):
- [ ] Ошибка при вводе неверного текущего пароля
- [ ] Новый пароль совпадает со старым паролем (запрет дублирования)
- [ ] Длина нового пароля: ровно 7 символов (граница снизу ➔ ошибка)
- [ ] Длина нового пароля: ровно 8 символов (минимальная граница ➔ успех)
- [ ] Длина нового пароля: 128 символов (максимальная граница ➔ успех)
- [ ] Длина нового пароля: 129 символов (граница сверху ➔ ошибка)
- [ ] Пароль без цифр / без букв верхнего регистра (проверка валидатора сложности)
- [ ] Несовпадение значений в полях "Новый пароль" и "Подтвердите новый пароль"

#### UX и безопасность:
- [ ] Маскирование паролей звездочками / точками
- [ ] Работа кнопки "Показать/скрыть пароль" (глазок)
- [ ] Защита от брутфорса (rate limit: блокировка ввода после 5 неудачных попыток на 15 минут)
- [ ] Запрет вставки пробелов в начале и конце пароля (trimming)
- [ ] Отправка формы по нажатию клавиши `Enter`
```

## 3. Таблица трассировки требований (Traceability Matrix)

Матрица связывает бизнес-требования из спецификации с тест-кейсами и баг-репортами, чтобы гарантировать 100% покрытие фичи:

| ID Требования | Описание требования | Покрывающие Тест-кейсы | Статус тестирования | Связанные баги |
| :--- | :--- | :--- | :---: | :---: |
| **REQ-01** | Регистрация по номеру телефона с СМС-кодом | `TC-REG-001`, `TC-REG-002` | ✅ Passed | — |
| **REQ-02** | Повторная отправка СМС не чаще, чем раз в 60 сек | `TC-REG-003` | ❌ Failed | `BUG-402` (таймер сбрасывается при F5) |
| **REQ-03** | Блокировка аккаунта после 3 неверных СМС-кодов | `TC-REG-004` | ✅ Passed | — |
| **REQ-04** | Применение реферального промокода при регистрации | `TC-REG-005`, `TC-REG-006` | ⏳ In Progress | — |
