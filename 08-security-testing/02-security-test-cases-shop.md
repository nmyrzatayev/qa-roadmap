# 🧪 Практические кейсы тестирования безопасности в QA Sandbox Shop

> В нашем учебном приложении **QA Sandbox Shop** смоделированы реальные уязвимости, которые часто встречаются в реальных интернет-магазинах. Ниже практические сценарии тестирования, которые вы можете воспроизвести и проверить прямо сейчас.

---

## 💥 Сценарий 1: Проверка Stored XSS в имени покупателя (Баг #10)

* **Уязвимый компонент:** `CheckoutModal.jsx` / Экран «Спасибо за заказ!».
* **Цель теста:** Проверить, экранирует ли система пользовательский ввод при рендеринге в DOM.

### Шаги тестирования:
1. В шапке сайта нажмите **🐞 Bug Hunter** и включите чекбокс **Баг #10: Хранимая XSS-уязвимость в поле имени покупателя**.
2. Добавьте любой товар в корзину и нажмите «Оформить заказ».
3. В поле **«ФИО получателя»** введите:
   ```html
   <img src="invalid-url" onerror="alert('ВНИМАНИЕ! XSS УЯЗВИМОСТЬ НА САЙТЕ!')">
   ```
4. Заполните остальные обязательные поля и нажмите **«Подтвердить и оплатить»**.

### Ожидаемый результат (Безопасный режим):
Браузер отображает введенную строку как обычный текст: `<img src="invalid-url" onerror=...>` без всплывающих окон.

### Фактический результат (В режиме бага):
Всплывает системный алерт браузера! В коде `completedOrder.customer.name` вставлен через опасный `dangerouslySetInnerHTML`. Если бы это был реальный прод, злоумышленник мог бы внедрить скрипт кражи cookies или перехвата номеров банковских карт!

## 💥 Сценарий 2: Подмена цен и отрицательные значения (Parameter Tampering)

* **Уязвимый компонент:** `POST /api/v1/orders/checkout`.
* **Цель теста:** Проверить, доверяет ли бэкенд переданным от клиента ценам, или берет актуальную цену строго из своей базы данных.

### Шаги тестирования через Postman или DevTools:
1. Откройте Postman.
2. Отправьте запрос на создание заказа:
   ```json
   POST /api/v1/orders/checkout
   {
     "customer": {
       "name": "Hacker",
       "email": "hack@sec.com",
       "phone": "+79990001122",
       "address": "Секретный бункер"
     },
     "items": [
       { "productId": 1, "quantity": -5 }
     ]
   }
   ```
3. Проверьте ответ бэкенда:
   - **Уязвимый бэкенд:** Уменьшает сумму корзины или начисляет баланс на склад!
   - **Защищенный бэкенд:** Возвращает ошибку `400 Bad Request: "Количество товара должно быть больше 0"`.

## 💥 Сценарий 3: SQL-инъекция в фильтрации каталога

* **Уязвимый компонент:** `GET /api/v1/products?search=...`.
* **Пейлоады для проверки:**
  ```text
  ' OR 1=1 --
  ' UNION SELECT username, password FROM users --
  '; DROP TABLE products; --
  ```

### Ожидаемый результат:
Поскольку бэкенд использует **TypeORM** и параметризованные запросы (`ILike(:search)`), база данных воспринимает введенные символы исключительно как строку поиска, не исполняя SQL-команды. Каталог просто вернет пустой список найденных товаров `[]`.

## 💥 Сценарий 4: IDOR (Доступ к чужому заказу по прямому идентификатору)

* **Сценарий:**
  1. Пользователь №1 оформил заказ и получил ID: `ORD-1711234567890`.
  2. Пользователь №2 вводит в адресную строку `http://localhost:5000/api/v1/orders/ORD-1711234567890`.
* **Проверка безопасности:**
  - Если запрос доступен публично без проверки принадлежности заказа текущему токену пользователя — это **уязвимость IDOR**.
  - Любой посторонний человек может выгрузить базу всех заказов конкурента, перебирая порядковые номера!
