## 1. Пирамида тестирования (Test Automation Pyramid)

Классическая концепция Майка Кона наглядно показывает баланс между скоростью, стоимостью и стабильностью тестов:

```
                  / \
                 / UI\          ◄── E2E / UI тесты (Playwright, Selenium)
                / E2E \             Медленные, дорогие, хрупкие (flaky). 10-15%
               /-------\
              /   API   \       ◄── Интеграционные / API тесты (REST, GraphQL)
             /Services / \          Быстрые, надежные, ловят бизнес-логику. 20-30%
            /-------------\
           /   Unit Tests  \    ◄── Модульные тесты разработчиков
          /_________________\       Мгновенные, дешевые, точечные. 60-70%
```

### Антипаттерн «Рожок мороженого» (Ice Cream Cone):
Когда у команды нет юнит-тестов и мало API-тестов, но написаны сотни тяжелых UI-автотестов, кликающих браузер:
- Сборка в CI бежит 3 часа.
- Тесты постоянно падают из-за задержек сети, всплывающих баннеров и изменений одного CSS-класса (**Flaky tests**).
- Доверие команды к автоматизации падает до нуля.

## 2. Когда НУЖНО и когда НЕЛЬЗЯ автоматизировать

| Автоматизировать СТОИТ ✅ | Автоматизировать НЕ СТОИТ ❌ |
| :--- | :--- |
| **Регрессионные тесты**, повторяющиеся каждый спринт | **Новый функционал**, требования к которому меняются каждый день |
| **Критический путь пользователя** (Smoke-тесты: регистрация, логин, оплата) | **Одноразовые проверки** или фичи для A/B теста на 1 неделю |
| **API эндпоинты** с большим объемом параметров и вариаций | **UX / Юзабилити / Дизайн** (насколько кнопка красива и гармонична) |
| **Трудоемкие проверки**: генерация сотен пользователей, парсинг больших отчетов | **Редкие краевые случаи (Edge cases)**, воспроизводящиеся раз в год |
| **Нагрузочное тестирование** (эмуляция 50 000 одновременных пользователей) | Тесты, написание и поддержка которых стоят дороже ручной проверки за 5 секунд |

## 3. Выбор стека технологий для автоматизации

Сегодня в автоматизации доминируют два ключевых направления: **TypeScript / JavaScript** и **Python** (а также классическая **Java** в корпоративном секторе).

| Направление | Инструмент UI | Инструмент API | Тест-раннер / Фреймворк |
| :--- | :--- | :--- | :--- |
| **TypeScript / JS** | **Playwright**, Cypress | Playwright API, Axios, Supertest | Playwright Test, Jest, Vitest |
| **Python** | **Playwright**, Selenium WebDriver | Requests, HTTPX | **Pytest** |
| **Java / Kotlin** | Selenide, Selenium WebDriver | RestAssured | JUnit 5, TestNG |

> [!TIP]
> **Рекомендация для новичка**:
> Начните с **Python + Pytest + Requests** (для тестирования API) либо **TypeScript + Playwright** (для сквозного тестирования API + Web UI). Playwright сейчас является индустриальным стандартом благодаря встроенному авто-ожиданию элементов (auto-waiting), параллельному запуску и поддержке современных браузеров без драйверов.

## 4. Базовые паттерны и концепции автоматизации

### 1. Локаторы (Locators)
Как тест находит элемент на странице:
- **По семантическим ролям (Best Practice в Playwright)**: `page.getByRole('button', { name: 'Submit' })` или `page.getByLabel('User Name')`.
- **По CSS-селекторам**: `page.locator('button.btn-primary')`.
- **По XPath**: `//button[contains(text(),'Submit')]` *(используется, когда нет других вариантов, но сложнее поддерживать)*.
- **По тестовым ID (Рекомендуется разработчикам)**: `data-testid="submit-order-button"`.

### 2. Паттерн Page Object Model (POM)
Разделение описания страниц приложения и логики самих тестов.
- Класс `LoginPage` хранит локаторы полей (email, password) и методы взаимодействия (`enterEmail()`, `clickSubmit()`).
- В самом тесте вызываются методы страницы, а не голые клики по селекторам. Если верстка изменится — локатор меняется в одном месте класса страницы, а не в 50 разных тестах.

### 3. Утверждения (Assertions)
Каждый тест обязан завершаться проверкой:
```python
# Пример в Pytest / Playwright (Python)
def test_user_can_login(page):
    page.goto("https://example.com/login")
    page.fill("#email", "tester@qa.com")
    page.fill("#password", "Secret123!")
    page.click("button[type='submit']")
    
    # Assert
    assert page.inner_text(".welcome-banner") == "Welcome, Tester!"
```

## 5. Основы CI/CD и запуск тестов

- **CI (Continuous Integration)**: Автоматическая сборка и прогон тестов на каждый коммит/Pull Request в репозиторий.
- **CD (Continuous Delivery / Deployment)**: Автоматическая доставка проверенного кода на тестовый или боевой сервер.

Если тесты автоматизированы, но запускаются только локально на ноутбуке тестировщика — пользы мало. Настоящая автоматизация работает в CI пайплайнах (GitHub Actions, GitLab CI, TeamCity, Jenkins).

```
   [ Разработчик делает Pull Request ]
                   │
                   ▼
       [ GitHub Actions / CI Runner ]
                   │
         ┌─────────┴─────────┐
         ▼                   ▼
    [ Linter ]         [ Unit Tests ]
         │                   │
         └─────────┬─────────┘
                   ▼
           [ API Auto-Tests ]
                   │
                   ▼
            [ UI Smoke Tests ]
                   │
            (Все зеленые ✅)
                   ▼
         [ Разрешен Merge в main ]
```
