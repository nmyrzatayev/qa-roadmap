# 01. Основы и теория тестирования ПО

> **Цель модуля**: Освоить ключевую терминологию, 7 базовых принципов тестирования и фундаментальные техники тест-дизайна, которые позволяют находить 80% багов при минимальном количестве тестов.

---

## 1. Разница между QA, QC и Testing

Очень часто эти термины смешивают, но между ними есть принципиальная разница в фокусе ответственности:

| Понятие | Что это | На что направлено | Вопрос, на который отвечает |
| :--- | :--- | :--- | :--- |
| **QA (Quality Assurance)** | Обеспечение качества | **Процессы**. Предотвращение дефектов на этапах аналитики, архитектуры, разработки. | *«Правильно ли мы строим процесс, чтобы дефекты не возникали?»* |
| **QC (Quality Control)** | Контроль качества | **Продукт**. Проверка готового продукта или промежуточного билда на соответствие требованиям. | *«Соответствует ли получившийся продукт заданным требованиям?»* |
| **Testing (Тестирование)** | Процесс проверки | **Действие**. Выполнение тестов, поиск расхождений между фактом и ожиданием. | *«Работает ли конкретная кнопка/функция так, как заявлено?»* |

## 2. Семь фундаментальных принципов тестирования (ISTQB)

1. **Тестирование демонстрирует наличие дефектов, а не их отсутствие.**
   *Тесты могут доказать наличие багов, но даже 1000 успешных тестов не доказывают, что программа абсолютно безошибочна.*
2. **Исчерпывающее тестирование невозможно.**
   *Нельзя протестировать все возможные комбинации входных данных и сценариев (например, поле ввода имени с триллионом вариантов строк). Нужны техники тест-дизайна и приоритеты.*
3. **Раннее тестирование.**
   *Чем раньше найден баг (в идеале — еще в ТЗ/требованиях), тем дешевле его исправление. Ошибка в архитектуре, найденная на проде, стоит в десятки раз дороже.*
4. **Скопление дефектов (Кластеризация дефектов).**
   *Принцип Парето в QA: ~80% дефектов обычно прячутся в ~20% модулей приложения (самых сложных или часто меняющихся).*
5. **Парадокс пестицида.**
   *Если повторять одни и те же тесты снова и снова, со временем они перестанут находить новые баги. Тестовые наборы нужно регулярно обновлять и обогащать.*
6. **Тестирование зависит от контекста.**
   *Банковское приложение для переводов, игра в жанре «три-в-ряд» и система управления медицинским аппаратом тестируются совершенно по-разному с разными стандартами надежности.*
7. **Заблуждение об отсутствии ошибок.**
   *Даже если система на 100% соответствует ТЗ и не падает, но решает не ту задачу пользователя или неудобна в работе — проект провален.*

## 3. Уровни тестирования

```
           ┌────────────────────────┐
           │     E2E / Acceptance   │  ◄── Тестирует пользовательский путь целиком
           ├────────────────────────┤
           │      System Test       │  ◄── Тестирует всю собранную систему
           ├────────────────────────┤
           │    Integration Test    │  ◄── Тестирует взаимодействие модулей / сервисов
           ├────────────────────────┤
           │       Unit Test        │  ◄── Тестирует отдельные функции / классы (обычно dev)
           └────────────────────────┘
```

1. **Unit (Модульное)**: Проверка минимальных изолированных кусочков кода (функции, методы). Пишется разработчиками.
2. **Integration (Интеграционное)**: Проверка взаимодействия между двумя и более модулями (например, сервис авторизации ↔ база данных, платежный шлюз ↔ бэкенд магазина).
3. **System (Системное)**: Проверка всей системы целиком в окружении, максимально приближенном к бою. Проверяются функциональные и нефункциональные требования.
4. **Acceptance (Приемочное / UAT)**: Проверка бизнес-заказчиком или фокус-группой пользователей: решает ли продукт реальные бизнес-задачи.

## 4. Классификация видов тестирования

### По запуску кода:
- **Статическое**: Анализ требований, документации, код-ревью без запуска самого приложения.
- **Динамическое**: Проверка программы во время её выполнения (клик по кнопкам, отправка запросов).

### По знанию внутреннего устройства (Box Testing):
- **Black-box (Черный ящик)**: Тестировщик знает только требования и спецификацию, не видя код.
- **White-box (Белый ящик)**: Тестировщик анализирует внутреннюю структуру, ветвления в коде, покрытие строк.
- **Grey-box (Серый ящик)**: Комбинация — знание архитектуры, структуры БД и API при тестировании через интерфейс или эндпоинты.

### Функциональное vs Нефункциональное:
- **Функциональное**: ЧТО делает система (Smoke, Sanity, регрессионное, интеграционное, позитивное/негативное).
- **Нефункциональное**: КАК система работает (Нагрузочное, Производительности, Безопасность, Usability, Совместимость, Доступность/a11y, Локализация).

## 5. Главные техники тест-дизайна с практическими примерами

Техники тест-дизайна отвечают на главный вопрос: **«Как написать минимум тестов, но проверить максимум возможных ситуаций?»**

### 1. Эквивалентное разбиение (Equivalence Partitioning)
Мы делим входные данные на классы, внутри которых поведение системы одинаково. Достаточно проверить одно значение из каждого класса.

> **Пример**: Поле ввода возраста покупателя алкоголя в интернет-магазине.
> - Требование: возраст от 18 до 100 лет включительно.
> - Класс 1 (Невалидный, слишком мал): `[-∞; 17]` ➔ Берем `14`.
> - Класс 2 (Валидный): `[18; 100]` ➔ Берем `25`.
> - Класс 3 (Невалидный, слишком велик): `[101; +∞]` ➔ Берем `110`.
> - Класс 4 (Невалидный тип данных): буквы, спецсимволы, пустое поле.

### 2. Анализ граничных значений (Boundary Value Analysis — BVA)
Большинство багов программистов происходят на границах диапазонов из-за ошибок в операторах `<` вместо `<=`.

> **Пример для того же возраста [18 .. 100]**:
> - Нижняя граница (18): Проверяем **17** (граница - 1), **18** (сама граница), **19** (граница + 1).
> - Верхняя граница (100): Проверяем **99** (граница - 1), **100** (сама граница), **101** (граница + 1).

### 3. Таблица решений (Decision Table)
Идеально подходит для систем со сложной комбинацией условий и бизнес-правил.

> **Пример**: Предоставление скидки клиенту банка:
> - Условие 1: Сумма покупки > 10 000 руб?
> - Условие 2: Есть премиум-карта?
> - Условие 3: Первая покупка в месяце?

| Правило | Сумма > 10к | Премиум-карта | Первая покупка | Результат: Скидка |
| :---: | :---: | :---: | :---: | :---: |
| 1 | ДА | ДА | ДА | **20%** |
| 2 | ДА | ДА | НЕТ | **15%** |
| 3 | ДА | НЕТ | ДА | **10%** |
| 4 | НЕТ | ДА | ДА | **5%** |
| 5 | НЕТ | НЕТ | НЕТ | **0%** |

Таблица гарантирует, что ни одна комбинация условий не будет упущена.

### 4. Диаграмма переходов состояний (State-Transition Testing)
Применяется, когда поведение объекта зависит от его текущего статуса (жизненный цикл заказа, тикета, брони).

```
               [ Создан ] ──(Оплата)──► [ Оплачен ] ──(Сборка)──► [ В пути ] ──(Вручение)──► [ Доставлен ]
                   │                         │
                   ▼                         ▼
             [ Отменен ]               [ Возврат средств ]
```
*Что тестируем*:
- Разрешенные переходы (пройти по зеленой стрелке).
- Запрещенные переходы: может ли заказ из статуса `[ В пути ]` перейти обратно в `[ Создан ]`? Что будет при двойном клике на «Оплатить»?

### 5. Попарное тестирование (Pairwise Testing)
Когда параметров много, тестировать все комбинации долго ($N^k$). Математически доказано, что подавляющее большинство дефектов проявляется при взаимодействии **пары** параметров. Инструменты типа *PICT* или *Allpairs* генерируют оптимальную матрицу.

### 6. Предугадывание ошибок (Error Guessing)
Неформальная техника, опирающаяся на интуицию и опыт тестировщика:
- Что будет при вводе эмодзи или иероглифов в поле ФИО?
- Что произойдет при вставке SQL-инъекции (`' OR 1=1 --`) или XSS (`<script>alert(1)</script>`)?
- Что произойдет, если обрезать сетевое соединение в момент отправки платежа?
