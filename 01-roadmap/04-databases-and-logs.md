## 1. Зачем тестировщику базы данных?

Графический интерфейс (UI) может врать или маскировать проблемы:
- Товар отображается как «Оплачен», но в БД статус остался `PENDING_PAYMENT`.
- Пользователь удалил аккаунт (soft delete), но его персональные данные не анонимизировались вопреки закону о защите данных (GDPR / 152-ФЗ).
- При оформлении заказа деньги списались, но запись в таблице `orders` не создалась из-за ошибки транзакции.
- Быстрая подготовка тестовых данных: создание пользователя с нужным балансом или правами напрямую через SQL.

## 2. SQL для QA: Практический минимум

### Базовая структура выборки (SELECT):
```sql
SELECT column1, column2 
FROM table_name 
WHERE condition 
ORDER BY column1 DESC 
LIMIT 10;
```

### Основные фильтры и операторы:
```sql
-- Фильтрация по статусу и диапазону дат
SELECT id, email, created_at 
FROM users 
WHERE status = 'ACTIVE' 
  AND created_at >= '2026-01-01'
  AND email LIKE '%@gmail.com';

-- Проверка на NULL (пустые значения)
SELECT id, phone 
FROM profiles 
WHERE phone IS NULL;

-- Поиск по списку значений
SELECT id, order_number, total_amount 
FROM orders 
WHERE status IN ('NEW', 'PROCESSING', 'PAID');
```

### Объединение таблиц (JOIN):
В реляционных БД данные распределены по связанным таблицам (например, `users` и `orders`).

```
  Таблица: users                Таблица: orders
  ┌────┬──────────────┐         ┌────┬─────────┬────────┐
  │ id │ name         │         │ id │ user_id │ amount │
  ├────┼──────────────┤         ├────┼─────────┼────────┤
  │ 1  │ Alice        │         │ 10 │ 1       │ 500    │
  │ 2  │ Bob          │         │ 11 │ 1       │ 1200   │
  │ 3  │ Charlie      │         │ 12 │ 2       │ 300    │
  └────┴──────────────┘         └────┴─────────┴────────┘
```

1. **`INNER JOIN`**: Возвращает только те строки, для которых есть совпадение в обеих таблицах (пользователи, у которых есть хотя бы один заказ):
   ```sql
   SELECT u.name, o.id AS order_id, o.amount
   FROM users u
   INNER JOIN orders o ON u.id = o.user_id;
   ```

2. **`LEFT JOIN`**: Возвращает ВСЕ строки из левой таблицы и совпавшие из правой. Если совпадений нет — в колонках правой таблицы будет `NULL`.
   *Отличный трюк для QA: как найти пользователей, которые никогда ничего не заказывали?*
   ```sql
   SELECT u.id, u.name
   FROM users u
   LEFT JOIN orders o ON u.id = o.user_id
   WHERE o.id IS NULL;
   ```

### Агрегатные функции и группировка:
```sql
-- Посчитать количество заказов и средний чек по каждому пользователю
SELECT user_id, COUNT(id) AS total_orders, AVG(amount) AS average_check
FROM orders
GROUP BY user_id
HAVING COUNT(id) > 5;
```

### ⚠️ Осторожность при модификации данных (INSERT / UPDATE / DELETE):
> [!CAUTION]
> **Золотое правило QA**: Никогда не выполняйте `UPDATE` или `DELETE` без условия `WHERE`! Всегда сначала напишите `SELECT ... WHERE ...`, убедитесь, что выбрана именно та запись, которую хотите изменить/удалить, и только потом применяйте команду.

## 3. Работа с логами: Где искать первопричину багов

Лог — это журнал событий программы. Когда приложение падает с ошибкой 500, в ответе API обычно написано лишь `{"message": "Internal Server Error"}`. Реальная причина спрятана в логах.

### Уровни логирования:
- `DEBUG`: подробные технические детали для разработки (вход в метод, значения переменных).
- `INFO`: штатные бизнес-события («Пользователь id=42 успешно авторизовался»).
- `WARN`: предупреждение, программа продолжает работать, но что-то пошло не так («Медленный ответ от внешнего сервиса геопозиции: 3.5s»).
- `ERROR`: ошибка выполнения конкретной операции («Ошибка сохранения заказа: Connection to DB timed out»).
- `FATAL / CRITICAL`: приложение не может продолжать работу и завершает процесс.

### Что искать в логе: **StackTrace**
Стек-трейс показывает цепочку вызовов методов, приведшую к аварии.
*Пример:*
```
NullPointerException: Cannot invoke "String.length()" because "user.getLastName()" is null
    at com.shop.service.UserService.validateProfile(UserService.java:84)
    at com.shop.controller.UserController.update(UserController.java:32)
```
Из этого лога сразу видно: на 84 строке файла `UserService.java` упала проверка фамилии, потому что пришло значение `null`. Программист починит это за 3 минуты.

## 4. Терминал (Linux / Bash / CLI) для тестировщика

Базовые команды, которые требуются на ежедневной основе:

| Команда | Описание | Пример использования в QA |
| :--- | :--- | :--- |
| `cd <path>` | Смена директории | `cd /var/log/application` |
| `ls -la` | Список файлов и папок с правами | Посмотреть список лог-файлов и их размер |
| `tail -f <file>` | Просмотр файла в реальном времени | `tail -f app.log` — воспроизводим баг в UI и сразу видим свежие строчки логов |
| `grep <text> <file>` | Поиск строки в файле | `grep -i "error" app.log` — найти все ошибки (без учета регистра) |
| `docker ps` | Список запущенных контейнеров | Узнать ID контейнера с бэкендом |
| `docker logs -f <id>` | Чтение логов контейнера | `docker logs -f backend-api --tail 100` |
| `curl` | Консольная отправка HTTP-запросов | `curl -X GET https://api.site.com/health` |

### Системы мониторинга и централизованных логов:
На крупных проектах логи не смотрят через консоль сервера, а собирают в централизованные системы:
- **ELK Stack (Elasticsearch, Logstash, Kibana)**: удобный поиск по логам микросервисов с фильтрацией по времени и ID сессии.
- **Grafana Loki / Prometheus**: мониторинг метрик, графиков нагрузок и логов.
- **Sentry**: система сбора необработанных крэшей и ошибок фронтенда и бэкенда с готовыми стек-трейсами.
