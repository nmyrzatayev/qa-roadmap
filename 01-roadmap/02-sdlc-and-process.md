# 02. Процессы разработки и артефакты тестирования

> **Цель модуля**: Понять, как устроена разработка в современных IT-компаниях, где место QA в жизненном цикле (SDLC / STLC) и как профессионально оформлять тестовую документацию (баг-репорты, чек-листы, тест-кейсы).

---

## 1. SDLC и STLC

- **SDLC (Software Development Life Cycle)** — жизненный цикл разработки ПО от идеи до вывода из эксплуатации.
- **STLC (Software Testing Life Cycle)** — жизненный цикл тестирования, являющийся неотъемлемой частью SDLC.

```
SDLC:
 [ Анализ требований ] ──► [ Проектирование ] ──► [ Разработка ] ──► [ Тестирование ] ──► [ Релиз / Деплой ] ──► [ Поддержка ]
                                                                             │
STLC:                                                                        ▼
 [ Анализ требований ] ──► [ Тест-планирование ] ──► [ Тест-дизайн ] ──► [ Выполнение тестов ] ──► [ Отчетность ] ──► [ Анализ итогов ]
```

### Главный сдвиг парадигмы: **Shift-Left Testing**
В классическом подходе (Waterfall) тестирование начиналось только после того, как программисты написали весь код. В современном подходе **Shift-Left** тестирование смещается влево: QA начинает тестировать уже на этапе согласования требований и макетов в Figma, находя логические противоречия задолго до написания первой строчки кода.

## 2. Методологии разработки: Scrum и Kanban

| Характеристика | Scrum | Kanban |
| :--- | :--- | :--- |
| **Отрезок времени** | Спринты (1–3 недели) | Непрерывный поток задач |
| **Планирование** | Обязательный Sprint Planning, фиксация скоупа | Задачи берутся по мере освобождения ресурсов |
| **Ограничения** | По времени спринта | По лимиту незавершенной работы (**WIP Limit**) |
| **Церемонии** | Daily Standup, Planning, Review/Demo, Retrospective | Стендап у доски, встречи по требованию |
| **Роль QA** | Тестирует внутри спринта, помогает команде закрыть цель спринта | Следит за прохождением задач через колонку "Testing" без образования бутылочного горлышка |

## 3. Базовые артефакты тестирования

### 1. Тест-план (Test Plan)
Стратегический документ, определяющий объем работ, подходы, ресурсы, графики тестирования и риски.
- **Scope (Объем)**: что тестируем (In-scope) и что НЕ тестируем (Out-of-scope).
- **Критерии входа/выхода (Entry / Exit criteria)**: условия, при которых мы начинаем тестирование (например: «билд задеплоен на стейджинг, Smoke-тесты зеленые») и заканчиваем (например: «0 блокирующих и критических багов, 95% тестов выполнено»).
- **Окружение (Test Environment)**: список браузеров, устройств, ОС, тестовых баз данных.

### 2. Чек-лист vs Тест-кейс

| Параметр | Чек-лист (Checklist) | Тест-кейс (Test Case) |
| :--- | :--- | :--- |
| **Что это** | Список того, ЧТО проверить (краткие тезисы) | Детальная инструкция с шагами и ожидаемым результатом |
| **Скорость написания** | Очень быстро | Требует времени |
| **Поддержка** | Легко поддерживать в актуальном состоянии | Требует регулярного обновления при малейших изменениях UI |
| **Когда использовать** | В быстрых Agile-командах, опытные тестировщики, регресс | Финансовые/медицинские проекты, передача тестов на аутсорс/новичкам, автоматизация |

### Анатомия Тест-кейса:
- **ID**: `TC-AUTH-001`
- **Title (Название)**: Четкое описание сути (например: *«Успешная авторизация по валидному email и паролю»*)
- **Preconditions (Предусловия)**: Пользователь зарегистрирован, находится на странице `/login`.
- **Steps (Шаги воспроизведения)**:
  1. Ввести валидный email в поле `Email`.
  2. Ввести валидный пароль в поле `Password`.
  3. Нажать кнопку `Войти`.
- **Expected Result (Ожидаемый результат)**: Происходит редирект в личный кабинет `/dashboard`, отображается приветствие с именем пользователя.
- **Postconditions (Постусловия)**: Выйти из аккаунта (очистка сессии).

## 4. Баг-репорт: Правило «Что? Где? Когда?»

Баг-репорт — визитная карточка тестировщика. Плохой баг-репорт возвращается со статусом *«Cannot Reproduce»*, хороший — берется в работу немедленно.

### Золотая формула Summary (Заголовка):
> **[Что сломалось] + [Где сломалось] + [При каких условиях]**
>
> ❌ *Плохо*: «Не работает кнопка»
> 
> ❌ *Плохо*: «Баг в корзине при покупке айфона»
> 
> ✅ *Хорошо*: «Ошибка 500 при нажатии кнопки 'Оформить заказ' при наличии в корзине товара с нулевым остатком»

### Обязательные поля баг-репорта:
1. **Summary (Заголовок)**: Четкий, емкий, по формуле.
2. **Severity (Серьезность)**: Насколько баг критичен для бизнеса/системы (Blocker, Critical, Major, Minor, Trivial).
3. **Priority (Приоритет)**: В какой очередности чинить (High, Medium, Low) — обычно выставляется PM/лидом.
4. **Environment (Окружение)**: ОС, браузер + версия, модель устройства, стенд (Dev, Staging, Prod), версия сборки/коммита.
5. **Steps to Reproduce (Шаги)**: Минимальные, воспроизводимые и однозначные шаги от 1-го лица без лишней "воды".
6. **Actual Result (Фактический результат)**: Что происходит на самом деле (с приведением кодов ошибок/текста).
7. **Expected Result (Ожидаемый результат)**: Что должно было произойти согласно требованиям/логике.
8. **Attachments (Вложения)**: Скриншот, скринкаст (видео), HAR-файл, логи консоли или бэкенда.

### В чем разница между Severity и Priority?
- **High Severity + Low Priority**: Внутренний сбой админ-панели, роняющий сервер при формировании годового бухгалтерского отчета 31 декабря. До декабря полгода, фиксить прямо сейчас не горит, но сам сбой критичен.
- **Low Severity + High Priority**: Опечатка в логотипе или названии компании на главной странице сайта банка. Никакой функционал не сломан, но бьет по репутации, поэтому приоритет исправления — наивысший.

## 5. Жизненный цикл бага (Bug Life Cycle)

```
 [ New / Open ] ──► [ Assigned ] ──► [ In Progress ] ──► [ Resolved / Fixed ]
                           │                                   │
                           ▼                                   ▼
                   [ Rejected / Invalid ]             [ Ready for Test ]
                           │                                   │
                           ▼                            ┌──────┴──────┐
                    [ Duplicate ]                       ▼             ▼
                                                   [ Reopened ]   [ Closed / Verified ]
```
